2 Dónde va cada archivo y por qué

Toda la carpeta va dentro de htdocs. La organización no es capricho: separa configuración, componentes reutilizables y recursos, que es justo lo que evalúa el instrumento de producto.

Por qué crear y actualizar llevan DOS archivos cada uno

Porque cada archivo hace una sola cosa. Uno muestra el formulario, el otro escribe en la base de datos. Es la misma regla de las carpetas, aplicada a los archivos.

OperaciónFormularioEscribe en la base
Crearregistrar.phpguardar.php
Leerconsultar.php — solo lee, no necesita segundo archivo
Actualizareditar.phpactualizar.php
Eliminareliminar.php — confirma y borra
La ventaja se nota cuando algo falla. ¿El formulario se ve mal? El problema está en registrar.php. ¿El dato no se guarda? Está en guardar.php. No hay que leer doscientas líneas para saber por dónde empezar a buscar.

El recorrido completo de un registro

registrar.phpmuestra el formulario
→
guardar.phpvalida e inserta
→
consultar.phpmuestra la lista

Si la validación falla, guardar.php devuelve al usuario a registrar.php con los errores y con lo que ya había escrito, para que no tenga que llenarlo todo otra vez.

Por qué la carpeta va exactamente en htdocs

Apache solo puede mostrar lo que esté dentro de htdocs. Si dejas el proyecto en el Escritorio y abres index.php con doble clic, el navegador te muestra el código PHP en texto plano en vez de ejecutarlo, porque nadie lo está procesando.

1. Navegadorpide la página
→
2. Apachela busca en htdocs
→
3. PHPejecuta el código
→
4. MySQLentrega los datos
→
5. Navegadormuestra el HTML

Entender este recorrido resuelve casi todos los errores: si algo falla, la pregunta es ¿en cuál de los 5 pasos se rompió?

4 Cómo se conecta la base de datos

Un solo archivo sabe conectarse; todos los demás se lo piden a él.

Los cinco datos de la conexión

DatoValorQué significa
DB_SERVIDOR127.0.0.1 En qué computador está MySQL. Es "este mismo"
DB_USUARIOroot Con qué cuenta entramos
DB_CLAVE(vacía) La contraseña de esa cuenta
DB_NOMBREmvp_ropa Cuál de todas las bases usamos
DB_PUERTO3306 Por cuál "puerta" escucha MySQL

Cómo lo usa cada página

// Una sola línea al principio del archivo…
require_once 'config/conexion.php';

// …y ya está disponible la variable $conexion
$consulta = $conexion->prepare('SELECT * FROM prendas WHERE id = ?');
Por qué está en un solo archivo. Si mañana cambia la contraseña de MySQL, se corrige aquí una vez y todo el sistema sigue funcionando. Si los datos estuvieran repetidos en cada página, habría que corregir 9 archivos y seguro se escapa alguno.

Por qué utf8mb4 aparece dos veces

Porque son dos cosas distintas, y las dos hacen falta:

DóndeQué haceSi falta…
En base_datos.sql Define cómo GUARDA los datos la base Las tildes se guardan dañadas
$conexion->set_charset() Define en qué "idioma" se hablan PHP y MySQL Las tildes llegan dañadas aunque estén bien guardadas

Síntoma típico de que falta una de las dos: ves CamisÃ³n en vez de Camisón.

Por qué todas las consultas usan bind_param

Nunca se pega el dato dentro del texto de la consulta. Si se escribiera "WHERE usuario = '$usuario'", alguien podría escribir ' OR '1'='1 en el formulario y entrar sin contraseña. Eso es una inyección SQL.

Con la consulta preparada, MySQL recibe primero la ORDEN (con ? en los huecos) y después los DATOS por separado. Como ya sabe cuál es la orden antes de ver los datos, trata lo que llega como texto y nunca como instrucción. 

// 1. La orden, con un hueco
$consulta = $conexion->prepare('SELECT * FROM prendas WHERE nombre = ?');

// 2. El dato, por aparte. La "s" dice que es texto (string)
$consulta->bind_param('s', $nombre);

// 3. Ejecutar
$consulta->execute();
LetraTipoSe usa para
sstringtexto: nombre, talla, color
iintegerenteros: id, stock
ddoubledecimales: precio
bblobarchivos binarios
El orden de las letras es sagrado. Debe coincidir exactamente con el orden de las variables. En guardar.php es "sssdis": nombre(s) talla(s) color(s) precio(d) stock(i) imagen(s). Si cambias una de puesto, el dato se guarda en la columna equivocada. Es el error más común de la sesión.

5 Cómo se conecta la API REST

Contenido de la Guía 2. El código está en includes/api_dolar.php y se ve funcionando en detalle.php.

Qué es una API REST

Página web normalAPI REST
DevuelveHTMLJSON
Para quiénPara que lo LEA una persona Para que lo USE un programa

El servicio que usamos

https://open.er-api.com/v6/latest/USD

Gratuito, sin registro ni clave. Devuelve algo así:

{
  "result": "success",
  "base_code": "USD",
  "rates": {
      "EUR": 0.92,
      "COP": 4150.25,   ← este es el dato que queremos
      "MXN": 17.05
  }
}

El dato está dentro de rates, en la casilla COP. Por eso en PHP se lee así: 

$datos = json_decode($respuesta, true);
$tasa  = $datos['rates']['COP'];

Las cuatro decisiones de diseño

Esta es la parte que más preguntan en la sustentación:

DecisiónPor qué
Límite de 5 segundos
CURLOPT_TIMEOUT		 Si la API está caída, sin este límite la página se quedaría cargando para siempre y el usuario no podría ni ver su inventario. Un servicio externo jamás puede bloquear tu sistema.
Caché de 1 hora Leer un archivo del disco tarda milésimas; consultar internet tarda segundos. Además, si 21 aprendices recargan 50 veces serían 1.050 consultas a un servicio gratuito ajeno, y muchas APIs bloquean por abuso. La tasa del dólar no cambia cada segundo.
Valor de respaldo Si la API falla, se muestra un aproximado avisando que lo es, en vez de romper la página. Mostrarlo como exacto sería engañar al usuario.
Se consulta DESPUÉS de la base de datos Lo esencial (la prenda) no depende de lo opcional (el dólar). Si fuera al revés, una API caída dejaría al usuario sin ver su propia información.

Los tres errores que hay que revisar

Un error de principiante es revisar solo si hubo respuesta. Pero un servidor puede responder perfectamente… con un mensaje de error. Por eso se revisan tres cosas distintas:

#Qué se revisaCómo
1¿Hubo conexión? $respuesta === false
2¿El servidor respondió con éxito? $codigo !== 200
3¿Lo que llegó es JSON válido y trae el dato? json_last_error() e isset()
Nunca pongas CURLOPT_SSL_VERIFYPEER en false. En muchos tutoriales de internet aparece así "para que funcione", pero eso desactiva la verificación del certificado y permite que alguien se haga pasar por la API. Si da error de certificado, se soluciona instalando el certificado, no apagando la verificación.

Cuando aparece un conflicto

Un conflicto pasa cuando dos personas modificaron las mismas líneas. Git no puede decidir cuál vale y te marca el archivo así: 

<<<<<<< HEAD
$precio = 45000;        ← lo que TÚ escribiste
=======
$precio = 50000;        ← lo que escribió tu compañero
>>>>>>> main

Para resolverlo:

  1. Abre el archivo y busca las marcas <<<
  2. Habla con tu compañero y decidan cuál queda (o si se combinan)
  3. Borra las tres líneas de marcas y deja solo el código correcto
  4. git add . y git commit -m "Resuelve conflicto en X"
Nunca borres el trabajo del otro sin hablar con él. Un conflicto no es un problema técnico, es un problema de comunicación del equipo. Se resuelve hablando.

10 Preguntas de la sustentación

Las que más caen, con la respuesta corta. El detalle completo está en los comentarios de cada archivo.

¿Por qué se validan los datos dos veces, en JavaScript y en PHP?

Porque hacen cosas distintas. JavaScript corre en el computador del usuario y se puede desactivar o saltar; valida por comodidad, para avisar rápido sin recargar. PHP corre en el servidor, donde el usuario no puede tocarlo; valida por seguridad. Si tuviera que quedarme con una sola, me quedo con la del servidor.

¿Qué es una consulta preparada y por qué la usan?

Es separar la orden de los datos: primero se manda la consulta con ? en los huecos y después los valores aparte. Como MySQL ya sabe cuál es la orden antes de ver los datos, trata lo que llega como texto y nunca como instrucción. Eso hace imposible la inyección SQL.

¿Por qué la contraseña se guarda con password_hash?

Porque el hash es de una sola vía: no se puede devolver al original. Si alguien roba la base de datos, no puede leer las contraseñas. Por eso la columna es VARCHAR(255) y no VARCHAR(20): lo que se guarda no es la contraseña sino su huella cifrada, que es mucho más larga.

¿Por qué el precio es DECIMAL y no FLOAT?

Porque FLOAT guarda números aproximados y con dinero eso produce errores de centavos que se van acumulando. Con dinero siempre se usa DECIMAL.

¿Por qué se redirige después de guardar?

Es el patrón PRG (Post-Redirect-Get). Si no se redirigiera y el usuario apretara F5, el navegador volvería a enviar el formulario y la prenda se guardaría dos veces.

¿Por qué eliminar pide confirmación?

Por dos razones. Para el usuario: borrar es irreversible y un clic mal dado no puede costar un registro. Técnica: una acción que modifica datos nunca debe ejecutarse con un enlace (GET), porque los navegadores y buscadores visitan enlaces por su cuenta. El borrado real solo ocurre por POST.

¿Qué pasa si la API del dólar no responde?

El sistema muestra un valor aproximado y avisa que lo es, en vez de romperse. Además hay un límite de 5 segundos para que no se quede cargando. Lo esencial no puede depender de un servicio de terceros.

¿Por qué el archivo de conexión no se sube a GitHub?

Porque tiene la contraseña de la base de datos y GitHub es público. Lo que sí se sube es conexion.ejemplo.php, con la misma estructura pero sin datos reales. Es una práctica profesional estándar: el código se comparte, las contraseñas no.

¿Qué significan las letras de bind_param?

Son el tipo de cada dato: s texto, i entero, d decimal, b binario. Va una letra por cada ?, en el mismo orden. En guardar.php es "sssdis".

¿Qué diferencia hay entre COUNT, SUM y GROUP BY?

COUNT cuenta filas, SUM suma valores. GROUP BY es lo que hace que esas cuentas se hagan por grupos: sin él, COUNT(*) cuenta toda la tabla; con GROUP BY talla, cuenta por cada talla por separado.
